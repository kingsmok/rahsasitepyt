# بروزرسانی کد و دیتابیس از GitHub

## وضعیت قابلیت‌ها

- **دستی:** مدیر از مسیر `پنل مدیریت ← مدیریت نصب و اتصالات` یا `/admin/update` ابتدا می‌تواند نسخه را بررسی و سپس بروزرسانی را اجرا کند.
- **اتوماتیک:** مسیر `/admin/update/webhook` برای Webhook نوع `push` گیت‌هاب در نظر گرفته شده است. فقط درخواست دارای `X-Hub-Signature-256` معتبر و Secret محیطی پذیرفته می‌شود.
- **مخزن خصوصی:** برای جلوگیری از لو رفتن PAT در گزارش‌ها، استفاده از SSH Deploy Key یا Secret محیطی توصیه می‌شود. URL دارای رمز/توکن در پنل و تاریخچه ماسک می‌شود.

## تنظیم Webhook

در `.env` سرور:

```env
GITHUB_WEBHOOK_SECRET=یک-رشته-تصادفی-طولانی
GIT_BRANCH=main
UPDATE_INSTALL_DEPENDENCIES=1
```

در GitHub از `Settings → Webhooks → Add webhook` این مقدارها را بگذارید:

- Payload URL: `https://DOMAIN.example/admin/update/webhook`
- Content type: `application/json`
- Secret: دقیقاً همان مقدار `GITHUB_WEBHOOK_SECRET`
- Events: فقط `Push`

بعد از تغییر `.env`، Passenger/Gunicorn را restart کنید. بدون Secret، Webhook عمداً غیرفعال است.

## ترتیب بروزرسانی

1. ارتباط با مخزن و شاخه بررسی می‌شود؛ اگر `GIT_BRANCH` خالی باشد default branch گیت یا شاخهٔ فعلی انتخاب می‌شود. روی گیت قدیمی سی‌پنل (بدون `--symref`) تشخیص از روی `main`/`master` یا API گیت‌هاب انجام می‌شود.
2. اگر پوشه از ZIP سی‌پنل نصب شده و `.git` ندارد، ابتدا `git init` و سپس fetch انجام می‌شود. اگر git در دسترس نباشد، آرشیو ZIP همان شاخه از GitHub دانلود و روی فایل‌ها کپی می‌شود.
3. فقط همان شاخه fetch می‌شود و فایل‌های ضروری `app.py`، `models.py` و `passenger_wsgi.py` بررسی می‌شوند.
4. کدها با commit تأییدشده جایگزین می‌شوند. `.env`، `instance/`، آپلودها، بکاپ‌ها، `.htaccess` و تاریخچهٔ محلی دست‌نخورده می‌مانند.
5. اگر `requirements.txt` تغییر کرده باشد، وابستگی‌ها نصب می‌شوند.
6. مایگریشن با یک Python process تازه اجرا می‌شود تا مدل‌های commit جدید واقعاً خوانده شوند.
7. Passenger برای reload لمس می‌شود و نتیجه در `instance/update_history.json` ثبت می‌شود.

## رفتار دیتابیس

مایگریشن فعلی **هیچ جدول یا رکورد موجودی را حذف نمی‌کند**:

- جدول‌های جدید از metadata مدل ساخته می‌شوند.
- ستون‌های جدید با نوع درست SQLite/MySQL اضافه می‌شوند.
- default مدل برای رکوردهای قدیمی ستون تازه backfill می‌شود.
- indexهای تعریف‌شده در مدل برای جدول‌های قدیمی نیز ساخته می‌شوند.
- قبل از مایگریشن، برای SQLite یک snapshot امن در `instance/backups/academy-update-*.db` ساخته می‌شود (پنج بکاپ آخر نگه داشته می‌شوند). در MySQL بکاپ کامل باید با پنل هاست/سرویس بکاپ انجام شود.
- اگر خطایی رخ دهد، بروزرسانی موفق اعلام نمی‌شود؛ گزارش خطا در وضعیت پنل و تاریخچه ثبت می‌شود.

تغییرهای پیچیدهٔ داده‌ای مثل تغییر معنای یک ستون یا ادغام دو ستون باید به‌صورت migration اختصاصی و قابل بازبینی به پروژه اضافه شوند؛ سیستم برای چنین تغییرهایی حدس مخرب نمی‌زند.

## اجرای دستی از خط فرمان

برای سرویس‌هایی که Webhook ندارند:

```bash
python updater.py --check
python updater.py --run
```

این دستور synchronous است و exit code صفر فقط در صورت موفقیت کامل برمی‌گرداند. عملیات وب پنل در Thread پس‌زمینه اجرا می‌شود تا timeout درخواست باعث قطع آن نشود.
